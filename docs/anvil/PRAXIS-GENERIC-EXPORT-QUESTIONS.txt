======================================================================
A. THE REQUIREMENT
======================================================================

The owner's requirement: Praxis export to Anvil must be available for EVERY approved Praxis task, not only the 200
frozen Golden KYC tasks. Anvil's deployed f50b9a8/schema077 export API accepts only the Golden profile and frozen
task sources, so every SME-authored task fails as PX_TASK_UNKNOWN or PX_TASK_PAYLOAD.

Praxis needs one versioned export contract that Anvil can validate (and later resolve) for:
  1. Any template:
     - KYC v1 (workbench) and KYC v2 (account opening, Golden structure);
     - the other Banking and Marketing templates;
     - forms uploaded by Admins as golden task packs (praxis.golden_pack.v1);
     - single-agent and multi-agent (workflow graph) tasks.
  2. Any approved task in a project: one task (validate before export) up to the whole project.
  3. The frozen Golden tasks, which stay supported exactly as today on their own profile.

What Praxis holds for each approved task (immutable, hash-chained record):
  - Header: task ID and revision; template and workflow; form ID and version; project; as-of date; language;
    jurisdiction or state; product.
  - Agent-visible content: brief (objective, assignment, deliverable); evidence records with stable IDs, source and
    date; parties and claimed roles; tool catalogue; recorded tool calls with arguments and responses (including
    error, 503/429 and pending observations); execution limits; assessment clock and calendar.
  - Bound policy: project rule versions (rule key, version ID, content hash, quotation, where each rule applies).
  - Private reference (never agent-visible): expected steps, findings, per-party assessment, follow-up rounds,
    reference outcome values, rationale, business hand-off.
  - Rubric: criteria with weights totalling 100, pass condition, partial-credit anchor (5/2/0), critical flag,
    evidence links, common errors and acceptable variations.
  - Provenance: author attestations, Expert and PM review decisions, synthetic-data declaration.
  - Where a criterion binds to an output field, Praxis also compiles a praxis.anvil.task.v1 contract (legacy,
    output-field grading).

Constraints Praxis keeps (owner decisions):
  - Evaluator-graded checks are NOT turned into agent-output fields.
  - Private expectations never enter the actor or public views.
  - valid:true is not approval; Praxis review status is not Anvil approval.
  - Paid model calls stay OFF for export, validation and resolution.

======================================================================
B. PRAXIS RESPONSE TO ANVIL'S PROPOSED BOUNDARY (points 1-7)
======================================================================

Praxis agrees with all seven points. Additions and precisions:

1. Generic validation. Agreed. Praxis declares two schema IDs per task: the form schema
   (praxis.template_profile.v1) and, for multi-agent, the graph schema (praxis.workflow_graph.v1-proposed). The
   package manifest schema is Praxis-proposed (praxis.authored-task-export.v1-proposed) until Anvil names its own.
   Unknown versions should return "unsupported contract", as Anvil proposes.

2. Form vs evaluator. Agreed. A Praxis form is versioned and immutable: a changed form gets a new form ID. Praxis
   sends the full form file with the package, so Anvil can register or match it explicitly. Praxis does not treat a
   form as an evaluator program.

3. Rubric. Agreed. Each criterion keeps its stable ID (C01...), weight, pass condition, partial-credit text,
   critical flag and evidence links. A missing evaluator mapping is Anvil readiness, not source invalidity.

4. Environment. Agreed. Recorded tool calls are evidence of the authored path, not an environment. Graphs may
   validate structurally and stay execution-blocked.

5. Private assets. Agreed. In the examples, the private file is a separate member with
   purpose: grader_only_reference_and_rubric and access: private_rubric. The actor file is Praxis's own server-side
   agent projection, which already removes every private field and private graph artifact. Praxis includes no
   executable code.

6. Separate states. Agreed. Praxis will show these as separate labels:
     package validity | Anvil readiness (environment/evaluators) | human/rights review | Run/paid authority
   Praxis will never trigger a Run.

7. Discovery, receipts, batching. Agreed. Praxis proposes that a large project export is split into independent
   packages within the published bounds. Each package carries a shared project batch ID and its own package ID and
   version. Anvil to confirm or specify.

======================================================================

Q1. PROFILE MODEL. How does a Praxis-authored task declare how it is evaluated?
    (a) Anvil publishes one generic "Praxis authored task" profile; or
    (b) Praxis submits each form (praxis.template_profile.v1, sent in the package) and Anvil registers and qualifies
        it as a profile; or
    (c) another mechanism.
    What profile ID and version format should Praxis put in the manifest, and how does Praxis learn that a form is
    registered or qualified (via /contracts)?

Q2. CRITERIA MAPPING. How does an authored criterion map to an Anvil evaluator configuration?
    The criterion holds: ID, weight, pass condition, partial-credit text, critical flag, evidence links, and an
    optional output-field binding.
    Options: run-evidence check, business table, trace check, human judge, or LLM judge (stays off while paid calls
    are off).
    Must weights be 5-point checks (20 x 5), or may Praxis send other weights totalling 100 (e.g. 40/30/30)?
    How should Praxis send the 5/2/0 anchors: free text in partialCredit today, or a structured field?

Q3. ENVIRONMENT. Recorded tool calls today are {id, tool, arguments, response, evidenceRef}.
    Should they become an MCP replay environment? Which manifest fields describe it (tools, actions/observations,
    reset, isolation)?
    Which logical environment hash, if any, should Praxis compute, and with which canonical JSON?
    (Golden uses Python json.dumps sort_keys; Praxis graphs use RFC 8785.)

Q4. PRIVATE CHANNEL. Is the separate private member inside the same ZIP acceptable (as in the examples), or must
    private assets go through a separate grader-only intake endpoint?
    Which purpose and access classifications should Praxis use?
    May the private member hold the complete authored task (as in the examples), or only the private fields?

Q5. PACKAGE FORMAT AND LIMITS.
    - Same ZIP envelope (manifest + files) with a new schema_version?
    - Required file layout and path rules (the examples use forms/, tasks/<id>/actor.json and
      private/<id>/reference.json)?
    - Limits: 1 MiB compressed, 30 MiB expanded, 1200 entries, 1-200 tasks? A project may hold more approved
      tasks; confirm the batching rule (section B.7).

Q6. RESPONSES AND CODES.
    Praxis will display errors[] (file, pointer, message, fix), anvil_requirements[] and review_gates[] separately,
    and keep auth, transport and internal errors apart.
    Please list:
    - the new PX_* codes for the generic path;
    - the new AV_* and REVIEW_* codes;
    - the result for an unsupported schema, form or profile.

Q7. DISCOVERY. Will GET /contracts list every supported schema, form or profile, with version, status
    (supported / registered / qualified) and limits? Praxis wants to tell a PM before export that a template is not
    yet supported by Anvil, instead of failing at validate.

Q8. RESOLUTION AND RECEIPTS. For the generic path:
    - Are the same Idempotency-Key, immutable receipt, 202 provisioning and package-version-conflict rules kept?
    - What does a receipt contain when a task validates but its evaluators or environment are not ready?
    - Is resolve per package or per batch?

Q9. DATES AND ORDER. When can Anvil QA accept a generic Praxis export, and in what order?
    Praxis suggests:
      (1) KYC v2 account-opening tasks (closest to Golden);
      (2) other single-agent sections forms;
      (3) multi-agent graphs.
    Which Anvil source revision and schema migration will carry it?

ADDENDUM 1 (12 Nov 2026, owner-confirmed approach): QUALIFY TEMPLATES, THEN VALIDATE TASKS
======================================================================

Owner's direction: every Praxis task is authored from a seeded template version, so the main check is whether that
TEMPLATE VERSION can be executed in Anvil for benchmarks. It must have enough to work on: inputs, policy and rule
binding, evaluations, environment, and tool and API calls. Per-task validation then becomes a light conformance
check. This replaces "validate arbitrary tasks" as the main ask in section C.

1. TWO LEVELS
   a) Template qualification: once per template version, by Anvil.
      Praxis sends the template version (form + execution declarations). Anvil returns:
        - qualified, with an immutable receipt; or
        - not qualified, with reasons split into Praxis fixes vs Anvil capability gaps.
      Praxis shows "Anvil-ready for benchmarks" (or why not) on the template, and warns before a PM creates a
      project from a version that is not qualified.
   b) Task validation: per task, at Validate and Export.
      The task must conform to its qualified template version and be complete and consistent:
        - cited rule versions are published;
        - every tool step has a recorded call;
        - criteria reference existing evidence;
        - private expectations are present.

2. WHAT A TEMPLATE VERSION MUST DECLARE TO BE EXECUTABLE
   - Inputs: evidence types, parties, as-of date and calendar.
   - Policy and rule binding: a citation field bound to published project rule versions (key, version ID, hash).
   - Evaluations: an evaluator kind for each rubric criterion, chosen from Anvil's catalogue. Anchors (5/2/0),
     weights, critical flags.
   - Environment and tool/API calls: each tool's input and output schema, error, 429/503 and pending behaviour,
     reset and isolation, and the environment adapter (e.g. MCP replay). Chosen from Anvil's catalogue.
   - Output: the final-answer schema (e.g. golden-kyc-recommendation-v1-style).
   - Multi-agent: graph node types, roles and handoffs supported by Anvil's runtime.

3. KNOWN PRAXIS-SIDE GAPS (Praxis will fix after agreement)
   - Most template tool catalogues are tool NAMES only. KYC v1 has full MCP tool schemas; KYC v2 and the other
     sections templates do not.
   - Rubric criteria have no evaluator kind; they hold free text plus anchors.
   - Graph node and handoff types have not been checked against Anvil's runtime.

4. OWNERSHIP OF THE TEMPLATE SPECIFICATION (Praxis proposal, owner to confirm with Anvil)
   - Praxis owns the template specification: the authoring form, guidance, coverage, review route, synthetic-data
     rules, and which tools, rules, criteria and outputs a task uses. Admins version templates in Praxis; templates
     are seeded or uploaded as packs.
   - Anvil owns the execution vocabulary and the qualification: a published, versioned capability catalogue
     (environment adapters, tool/API schemas, evaluator kinds, output schemas, run limits), and the qualification
     receipt per template version.
   - Rule: a Praxis template may reference only capabilities Anvil has published.
   - Change: a Praxis template change is a new template version, which needs new qualification; projects keep the
     receipt of their version. An Anvil capability change is a new capability version; existing receipts stay valid
     until Anvil explicitly revokes them.

5. GENERATING TEMPLATES FROM A SPECIFICATION (Praxis capability, later)
   Praxis will be able to draft a template version from:
     - a domain specification (like the Golden KYC reference); plus
     - Anvil's capability catalogue (tool schemas and evaluator kinds are picked from it, never invented).
   The draft passes Praxis's form checks, then Anvil qualification, then an Admin publishes it. Any AI-assisted
   drafting stays a draft until a person publishes it. Paid model use for drafting is a separate owner decision.
