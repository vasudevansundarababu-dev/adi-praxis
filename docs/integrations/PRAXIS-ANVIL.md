# Praxis to Anvil executable handoff

Initial build: `test-1.2-praxis-harbor-20261030` (single and staged structured decisions; live model verification remains separate).

The frozen `contracts/praxis/task.schema.json` and original synthetic marketing fixture are shared with Anvil. Schema version `praxis.anvil.task.v1` is separate from `task_version` and `revision_id`. The v2 schema is `task-v2.schema.json`; `synthetic-marketing-staged.task.json` adds a two-stage decision with a future budget reveal and state projection. Original fixture is a software test draft, not human approval or reviewed rights clearance.

Authors open any generic authoring task and select **Start a synthetic executable marketing example**. They inspect and edit its objective, evidence, constraint bindings, initial state, actions, stage, deliverable, criteria and reference output. Autosave, revision conflict handling, synthetic declaration, data scan, duplicate checks, submission versions and independent review use the existing application services. Marketing / Structured decision authoring requires a contract. Other existing workflows retain their own definitions; an attached executable contract is also validated.

V1 supports a single local structured decision, one `output.json` deliverable and allowlisted equality/numeric lower/numeric upper bounds. Actions and completion text describe file submission; they do not execute arbitrary code. V1 rejects multiple stages and future visibility. V2 uses `praxis.anvil.task.v2` / `staged-decision-v1`, two to twelve ordered submit-json stages, per-stage rules and rubrics, future evidence tied to a later stage, and finite scalar state projections. References to unavailable/private evidence, missing actions and invalid state projections fail closed. Alternate runtimes remain unsupported. Reference output must satisfy every rule. Cross-object IDs are unique; weights total 10000. Private evidence cannot be referenced by the actor stage.

Administrators open **Projects → Approved exports** and download a task JSON. Existing NDJSON export is preserved. The UI downloads an optional `praxis.anvil.export.v1` envelope (`?envelope=true`) containing the exact canonical task bytes in `payload_json`, its SHA-256, and source record/project/client/submission/reviewer metadata. Anvil verifies the hash and preserves the envelope as a hidden immutable receipt; this does not convey rights approval. Default raw export remains supported. The versioned endpoint is `GET /api/v1/dataset/records/:id/praxis-contract`; both Admin sessions and existing RL_GYM API clients use tenant authorization. It exports only the explicit contract stored in that immutable approved record, without automatically joining private source uploads. It verifies the source record hash before export. Headers retain `x-praxis-payload-sha256`, `x-praxis-record-id`, `x-praxis-record-hash` and schema version. Download `/dataset/records/:id/lineage` for reviewer and submission traceability. Anvil must preserve exact received bytes and hash, and independently qualify the package and review rights.

No historical accepted record is backfilled. Corrections append a new record and revalidate executable content; an existing contract cannot be removed via correction. Original record schema and canonicalization remain version 1, preserving historical hashes. No database migration is required.

The existing demo setup job idempotently creates a clearly labeled synthetic Marketing template and two DRAFT projects with unassigned CREATED example tasks through application APIs. Repeated setup preserves the same drafts and writes an audit event. It does not assign a fictional person, accept contributor terms or create task/rights approvals. PM staffing and real author/reviewer actions remain required. Built-in example loading generates new task/revision identifiers and resets source review to draft. Automated test identities exercise the complete application workflow only in the isolated test database.

The four earlier Library specification references were not re-materialized in this implementation. This is a frozen executable increment, not a claim that all 230 field mappings or the complete original staged intake specification have been reconciled.

The explicitly labeled software-fixture route `GET /projects/:id/synthetic-example` downloads an unassigned CREATED synthetic example only in local/demo DRAFT test projects. It is separate from accepted-record export and carries draft status/task identity/hash headers. PMs can download it from Tasks and invites for non-human software qualification. It must never be treated as an approved dataset record or a rights grant.
