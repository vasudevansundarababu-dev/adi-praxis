# Policy snapshot sidecar v2 (proposed)

Status: **proposed**, for Anvil to validate. Schema: `contracts/praxis/policy-snapshot.v2.schema.json`.
`schema_version: "praxis.anvil.policy.v2-proposed"`.

v1 (`praxis.anvil.policy.v1-proposed`, `policy-snapshot.schema.json`) and the READY v1 package on branch
`handoff/anvil-seed-export` are unchanged. Anvil keeps v1 pinned until it accepts v2. Praxis's live export routes
(`/studio-tasks/export`, `/dataset/export`) still send v1; v2 is produced by the SEED exporter only, until Anvil agrees.

## Why v2

In v1, a rule's `content_hash` included the database ID of the cited document version, and `digest` covered rule-set and
change IDs. A reseed of identical content therefore produced new hashes. v2 separates two kinds of identity:

| Content identity (hashed) | Database identity (`provenance`, never hashed) |
|---|---|
| What a rule says, and which document **bytes** and quotes it cites | `rule_id`, `rule_version_id`, `document_version_id`, `snapshot_id`, `task_instance_id`, `change_id`, rule-set ID, versions, `published_at`, rubric version, the v1 `content_hash` and `digest` |

Unchanged content keeps its hashes across reseeds. Whole export files still differ, because provenance changes.

## Hash definition (`hash_algorithm: "praxis.content-hash.v1"`)

```
content_hash(x) = lowercase_hex( SHA-256( UTF-8( JCS(x) ) ) )
```

`JCS` is the JSON Canonicalization Scheme, [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785): object keys sorted by
UTF-16 code units, no whitespace, ECMAScript number formatting, minimal string escaping. Array order is kept, so where
order carries no meaning the input below sorts the array first. Praxis checks its implementation against the RFC 8785
key-sorting and number vectors in `apps/api/test/policy-snapshot-v2.test.ts`.

### Rule

`rules[].content_hash = content_hash(rule_input)`, where `rule_input` is:

```json
{
  "rule_key": "...", "title": "...", "requirement": "...", "requirement_type": "...", "visibility": "...",
  "applicability": {}, "prerequisites": [], "precedence": [], "exceptions": {}, "effective": {},
  "evidence_needs": [], "verification_hint": null,
  "sources": [{ "document_sha256": "...", "field": "...", "role": "...", "quote": "..." }]
}
```

- Every value is copied exactly as it appears in the exported rule.
- `sources` is sorted by the canonical JSON of `[document_sha256, field, role, quote]`.
- `document_sha256` is the SHA-256 of the cited document's original bytes. This is the rule's source binding.
- Not hashed: `applicability_label` (derived display text), `locator` (a re-extraction can move a quote without
  changing it), and every `provenance` object.

### Task change

`task_changes[].content_hash = content_hash(change_input)`, where `change_input` is the change without
`content_hash` and `provenance`:

```json
{ "rule_key": "...", "rule_content_hash": "...", "type": "...", "requirement": "...", "scope": {}, "reason": "...", "exception_index": null }
```

`rule_content_hash` ties the change to the exact rule content it modifies.

### Snapshot

```
content_hash = content_hash({ "rules": sort(rules[].content_hash), "task_changes": sort(task_changes[].content_hash) })
```

The task's identity in the package is `task_ref` (for example `SEED-PHONE-001`). The task contract has its own
`task_payload_sha256` in `index.json`.

## Verifying a package

1. Check every file against `MANIFEST.sha256`: `cd anvil && shasum -a 256 -c MANIFEST.sha256`.
2. For each document in `index.json`, check that SHA-256 of the file equals its `sha256`. Every rule source's
   `document_sha256` must equal the published document's hash.
3. Recompute each rule, change and snapshot `content_hash` from the definitions above and compare.

## Example

`seed-export/examples/hash-stability.json` in the v2 package is generated by the exporter. It seeds the same fictional
content twice:

- **Same content:** the same rule from two seeds has different `rule_version_id`, `document_version_id` and
  `snapshot_id`, but the same rule `content_hash` and snapshot `content_hash`.
- **Changed content:** one sentence is added to that rule's requirement. The rule hash and the snapshot hash change;
  every other rule's hash stays the same.

Changing a quote, or citing different document bytes, also changes the rule hash. Changing an ID, a locator, the display
label or the publish time does not. Both are covered by the tests.
