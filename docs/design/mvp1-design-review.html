PM and Admin journey

All in the console. Menu for MVP1: Home, Projects, Sourcing, Admin, Tutorials.

  1. Create a project from a templateProjects › New projectOpen screen ↗
    • The existing six-step wizard, unchanged: Template, Basics, Volume and TPT, Demographics, Job description, Review and submit.
    • Choose the review route here: Author → PM/Admin, or Author → Reviewer → PM/Admin. It is read-only afterwards.
    • Submitting creates exactly the number of tasks the template defines (for KYC v6: one per state, CA, NY, TX, FL, IL).
  2. Upload policies and publish the rulesProject › PoliciesOpen screen ↗
    • Add the federal and state policy documents; extraction (LlamaExtract or Google) proposes rules with citations.
    • Suggest rules, tick Apply to project (that is the human review), then publish the rule set. Every task inherits it.
  3. Create the opportunity: Export to RecruiterProject › Resource assignmentsOpen screen ↗
    • One button, one PDF, built from the project: 1 the role, 2 requirements with the evidence to check, 3 the SME cheat sheet (the task they would author, in plain words), 4 what to send back for each candidate.
    • Attached inside the PDF: a candidate assessment sheet (Excel), one row per candidate: first and last name, Gmail address, an assessment per requirement, answers to the questions, why they fit. "Download Excel only" gives the same sheet for viewers that hide attachments.
    • No Publish and no public apply link. The pack goes to recruitment agencies.
  4. Agencies recruit offlineOutside Praxis
    • The agency interviews candidates against the JD and the tasks, and sends back the profiles that match, with the candidates' answers.
  5. Upload the profilesSourcing › NewOpen screen ↗
    • Upload the recruiter's filled assessment sheet (one profile per row), or add one person: project (only New or active ones), first name, last name, email; optional LinkedIn URL, CV and assessment. Accepted in good faith.
    • SMEs and Reviewers are uploaded the same way. The Sourcing list has search by name, email, role or skill.
    Open the Sourcing list ↗
  6. Assign people to tasksProject › Resource assignments › AssignOpen screen ↗
    • Lists Sourcing profiles whose skills match the template. Choose the task, then Assign as SME (an open task to author) or Assign as Reviewer (only on the Reviewer route; never their own task).
    • Assigning is the selection; there is no separate screening. SMEs are capped at Required workers.
    • In Online sign-in mode, a new person gets an email with a one-time link to set their password.
  7. Track progressProject › Dashboard, Resource assignments, TasksOpen screen ↗
    • Dashboard: experts, tasks approved, rule set, rework rate; a Next step banner; coverage by state.
    • Resource assignments: each person's role, task ID and task status. Tasks: one row per task with author, status and date.
  8. Review and decideProject › Tasks › task pageOpen screen ↗
    • Any task name opens the authored form. On a submitted task: Approve, Rework or Reject (Rework and Reject need a comment).
    • On the Reviewer route the Reviewer goes first; the PM or Admin makes the final call. Approve adds the task to the approved dataset.
  9. Validate and export to AnvilProject › TasksOpen screen ↗
    • Validate on any approved task, at any time (checks it with Anvil; the screen says "RL Gym"). "Valid" is not approval or Anvil readiness.
    • Export to RL Gym opens only when every task in the project is approved, and sends them to Anvil as one batch.
  10. Admin settingsAdminOpen screen ↗
    • New: Candidate app sign-in, Offline (email and name, test environments only) or Online (email and password).
    • Unchanged: Users (add user, reset password), Taxonomy, Terms, Failure codes, API clients.

Candidate and Reviewer journey

The candidate app shows only Home and Sign out. A person's role on each project comes from how they were assigned: as SME, as Reviewer, or both across different projects.

  1. Get accessEmail (Online mode)
    • Online: a welcome email with a one-time, expiring link to set a password. The username is the Gmail address the agency gave.
    • Offline (QA and demos): no email; the person signs in with their email and name.
  2. Sign inSign inOffline ↗Online ↗
    • 18+ confirmation the first time. An email that was never uploaded sees "No tasks for this account".
  3. Accept the terms, onceBefore you startOpen screen ↗
    • Contributor terms (confidentiality, IP, data use) and "synthetic data only". Recorded with the terms version. No identity check in MVP1.
  4. See their tasksHomeOpen screen ↗
    • A Next step card (rework first), then every assigned task: New, Rework, In review, Accepted or Rejected.
  5. Author the taskTask pageOpen screen ↗
    • The template's form, section by section, with an example line for each. Saves as they type; Submit for review.
    • Tutorial: the video for this task's template. Help: an AI chat about this task only. It explains and gives examples, never writes the task, and refuses anything outside it.
  6. Fix a reworkTask pageOpen screen ↗
    • Each reviewer comment shows under its own section, which is highlighted. Resubmit for review.
  7. Review a task (when assigned as Reviewer)Home › Tasks to reviewOpen screen ↗
    • The authored form, read-only, with a comment box under each section.
    • Send back for rework (needs a comment) returns it to the SME. Approve sends it to the PM or Admin to accept and export.
    Open a Reviewer's Home ↗
  8. Follow the outcomeHome
    • In review while it is checked, then Accepted or Rejected (with the reason). Accepted tasks are read-only.

What MVP1 includes, and what waits

In MVP1
  • Project page with four tabs: Dashboard, Resource assignments, Tasks, Policies.
  • JD export (PDF), Sourcing upload and search, assigning people to tasks.
  • Task review by the PM or Admin, with the Reviewer route where the project uses it.
  • Per-task Anvil validation; export when all tasks are approved.
  • Candidate app: sign-in (Offline or Online), terms, task list, authoring, Tutorial, Help, rework, Reviewer view.
Hidden until after MVP1
  • Opportunities, public apply links and the applicant journey.
  • Reviews menu (candidate review moves into Sourcing later).
  • Certification and SME training, Partners, Payments.
  • Identity check (Stripe).
  • Recruiter-answer validation; Partner upload screen.

Decisions behind this design

DecisionDetail
RecruitingAgencies only, offline. PM or Admin uploads profiles; required fields are project, first and last name, email.
Who assignsAlways the PM or Admin: people to the project and to each task, SME or Reviewer.
Review routeSet at project creation, read-only. Reviewers exist only on Author → Reviewer → PM/Admin.
Task tableExactly the number of tasks the project defines; no Add task, no Invites, no task inputs.
CoverageFollows the template's selector. KYC v6: by state; the scenario is the author's choice inside the task. Pending with Anvil: a KYC v7 where application type (Single, Joint, Minor, Custodian) selects the task and state is an optional example; coverage would then be by application type. Not agreed yet.
ExportOnly when every task is approved. Per-task validation any time. Today's code also allows "marked complete" or "end date"; both go, and the Anvil contract text is updated with Keystone.
ReviewersExternal experts who sign in like SMEs, in the candidate app.
Sign-inAdmin switch: Offline (no password, refused in production) or Online (password set by an emailed one-time link, never a password in email).
Terms and identityTerms accepted once at first sign-in. No identity check in MVP1.
Help and TutorialBoth linked to the task. Help answers about the task only and never writes it.
Public names (legal)No "ADI-Labs", "Praxis" or "Anvil" on any screen, PDF or email. The product is ADI Forge; Anvil appears as "RL Gym"; the ADI-Labs tagline is removed. Code, APIs, schema names and internal documents keep their names, and the Anvil integration is unchanged.
Admin pagesTaxonomy (wizard step 4 and JD requirements), Terms (accepted at first sign-in), Failure codes (RL reviews, not used in MVP1) and API clients (Anvil and RL Gym keys) stay unchanged. A current Terms version must be published before any SME signs in.

How it gets built

No breakages. New screens are added next to the old ones behind a setting; nothing is deleted until its replacement is live and tested. Menus are hidden, data and pages stay. Every step ships with tests (mocks only), the full test suite passing, and the QA smoke test passing before and after deploy.

OrderStepWhy first
1PM or Admin assigns a person to a specific task; that assignment counts as the selectionUnlocks authoring without the applicant journey
2Tasks tab review page (Approve, Rework, Reject, comments per section)Must exist before the Reviews menu is hidden
3Candidate Home: the task list with New and ReworkThe SME's way in
4Export rule "all tasks approved"Completes the loop; needs Anvil switched on
5Sourcing; Online sign-in with set-password links; Reviewer view in the candidate app; task Tutorial and Help; menu clean-upFollow once the loop works

Outside Praxis: Anvil has to switch on its side of the export (its contract, plus the export key) before validation and export can finish in QA. Today the smoke test skips export for this reason.
